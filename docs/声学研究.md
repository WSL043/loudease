# 声学研究和优化路线

> 历史研究日志：包含已退役的页面级音频链路与早期参数，不是现行实现说明。当前算法以 [`AUDIO_DSP.md`](AUDIO_DSP.md) 为准。

目标：做浏览器级音量平衡，而不是暴力放大器。插件应该让网页声音更稳定、更不刺耳，同时尽量保留原视频的层次和音质。

## 当时结论（已被现行架构部分取代）

1. 音量平衡要分成两层：
   - 慢速 leveling：根据短时响度把整体听感拉向目标。
   - 快速 limiter：只处理突然尖峰，防止爆音和破音。

2. 测量不能只看 sample peak：
   - sample peak 适合兜底限峰，不适合判断“听起来大不大”。
   - 响度判断要看短窗口 RMS、滚动分布、静音门限和峰值余量。

3. 小声不能无限拉大：
   - 小声提升会同时放大底噪、混响、压缩失真和原视频破音。
   - 提升必须受峰值余量限制，宁愿少提一点，也不能把声音推爆。

4. 不应强迫刷新抖音/B站这类随机流：
   - WebAudio 对同一个媒体元素的 `MediaElementSource` 有浏览器限制。
   - 已被旧音频链路接管的当前 video 不能保证无损二次接管。
   - UI 应优先保持当前播放，等待新媒体元素出现时重新接管，而不是默认刷新页面。

5. “更大声”不等于“更好听”：
   - 平台级响度归一化通常优先把大声内容降下来，而不是无条件把小声内容推上去。
   - 小声提升必须看 true peak / sample peak 余量，否则会把编码失真、齿音、底噪一起放大。
   - 对短视频来说，用户感知最差的不是整体偏小，而是下一条突然爆、以及一句话内部忽大忽小。

## 2026-06-30 研究增量

### ITU-R BS.1770 的启发

BS.1770 的核心不是“看最大峰值”，而是用 K-weighting 后的能量估计主观响度，并用 400 ms gating block 做统计。  
对本扩展的启发：

- 当前 8 ms 控制周期适合做快速保护，不适合直接代表听感响度。
- 应增加一个 300-500 ms 的“听感响度窗口”，作为主 leveling 输入。
- 8-16 ms 瞬时峰值只交给 limiter 和瞬态保护，不应该决定长期增益。
- 后续 K-weighting 可以先做近似：high-pass + high-shelf，等稳定后再实现更接近标准的滤波器系数。

### EBU R128 / Loudness Range 的启发

R128 不是要消灭所有动态，而是把平均响度、响度范围和最大真峰值分开管理。  
对本扩展的启发：

- 插件不能把 1% 到 100% 的所有声音机械拉成完全同一个 sample level。
- 更合理目标是压缩“过大的差距”，但保留语气、音乐起伏和视频原本层次。
- 后续可以维护一个滚动 loudness range：如果最近 3-10 秒差距太大，再加大处理；如果素材本来已经稳定，就少动。

### Spotify 播放端策略的启发

Spotify 官方说明其普通响度目标是 -14 LUFS，安静模式约 -19 LUFS，响亮模式约 -11 LUFS；负增益不会增加失真，正增益要看 true peak 余量，响亮模式才会使用 limiter。  
对本扩展的启发：

- 默认策略应偏向 downward：先压大声，少量托小声。
- 正增益提升要比负增益保守，因为它更容易引入削波和失真。
- UI 里“提小声”不应叫增强、放大或音量；它本质是有条件的细节托起。

### WebAudio 实时处理限制

浏览器实时处理和离线母带处理不同：

- 不能提前知道整段视频的 integrated loudness。
- 不能高延迟前视，否则视频口型和声音会错位。
- 同一个 `HTMLMediaElement` 的 `MediaElementSource` 连接存在浏览器限制，旧连接无法总是无损热替换。
- 因此算法要依赖短窗口、滚动统计和保守 limiter，而不是一次性全曲分析。

## 参考依据

- ITU-R BS.1770：广播响度和 true-peak 测量的基础标准，适合作为后续 K-weighting / true peak 方向参考。  
  https://www.itu.int/rec/R-REC-BS.1770

- EBU R128：响度归一化的工程实践参考，核心思想是用响度而不是单点峰值管理听感。  
  https://tech.ebu.ch/publications/r128

- Spotify Loudness normalization：播放平台对 integrated LUFS、True Peak 和正增益风险的工程参考。  
  https://support.spotify.com/us/artists/article/loudness-normalization/

- Web Audio API：说明媒体元素接入 WebAudio 图后的行为边界，后续要围绕浏览器限制设计恢复策略。  
  https://www.w3.org/TR/webaudio/

- YouTube Stable Volume：用户目标层面的参考，方向是减少视频内外音量差异，而不是把所有声音粗暴放大。  
  https://support.google.com/youtube/

## 后续算法路线

### v1 稳定线

- 保持当前 `GainNode` 实时增益控制。
- 保持原生 `DynamicsCompressorNode` 只作为辅助平滑层。
- limiter 只兜底，不参与长期音量判断。
- “压大声”和“提小声”仍然分开，避免用户把小声提升当作总音量增强。

### v2 音质线

- 增加 K-weighting 近似滤波，让响度判断更接近人耳。
- 用 percentile / gated loudness 替代简单平均，减少短促尖峰误导。
- 增加 true-peak 近似检测，降低小声提升后的隐藏削波风险。
- 分离三个信号：
  - momentary loudness：300-500 ms，决定主要增益。
  - transient peak：8-16 ms，决定 limiter / 快速削峰。
  - rolling range：3-10 秒，决定当前素材是否需要更强平衡。

### v3 智能线

- 识别说话、人声主导、音乐主导、强噪声几类状态，但不暴露成复杂模式。
- UI 仍只保留少量控制，复杂策略放到后台自动选择。
- 诊断页面记录当前算法状态，普通 popup 不显示调试信息。

## 下一轮实验计划

### 已应用：0.4.36

- 实验 A 已落地第一版：主响度判断从 16/40ms 改为约 400ms 窗口。
- 实验 C 已落地第一版：小声提升使用最近峰值余量，不只看当前 8ms 的瞬时峰值。
- 正增益响应放慢到更接近几十毫秒，减少字尾、噪声尾巴被突然拉起。
- 瞬态保护仍保留毫秒级，避免大声先漏出来。

### 已应用：0.4.37

- 抖音这类信息流页面会保留旧 video 和预加载 video。旧媒体元素的 `MediaElementSource` 占用错误不再污染整页状态。
- 只有当前正在发声的媒体元素接管失败，才把页面标为“当前视频受限”。

### 已应用：0.4.38

- 实时诊断确认：抖音当前发声 video 失败时，错误是 Chrome 拒绝对同一个 `HTMLMediaElement` 再创建 `MediaElementSourceNode`。
- 根因不是单纯 UI 误报，而是扩展在用户手势解锁后会接管暂停但可见/已加载的预热视频。抖音复用这些 video 后，旧失败或旧连接会带到真正播放的视频。
- 修复：后台扫描和用户手势解锁不再接管暂停预热视频；只保留 `play()` 钩子和播放中扫描作为接管入口。

### 已应用：0.4.39

- 二次审查确认：`MediaProcessor` 构造函数仍会直接调用 `attach()`，实际绕过了 0.4.38 的“后台扫描跳过暂停预热视频”判断。
- 修复：构造函数只绑定事件，不再立即接管；只有 `play` / `playing` 或播放中扫描才会触发接管。
- 抖音复用同一个 video DOM 时，如果旧 `src` 的 `already connected` 失败还挂在处理器上，会误报为当前视频受限。
- 修复：失败状态现在记录并比对 `lastErrorSrc`，旧 `src` 失败会被清掉并允许当前 `src` 重新尝试；后台聚合也只把当前 `src` 的失败算作“当前视频受限”。

### 已应用：0.4.40

- 二次审查确认：旧逻辑把安全 limiter 完全绑定到“压大声”强度。用户把“压大声”设为 0、但“提小声”仍开启时，可能出现正增益没有 limiter 兜底。
- 修复：limiter 改为跟随“压大声”和“提小声”两者中的较大强度。只有两个强度都为 0 时才完全关闭 limiter。

### 已应用：0.4.41

- 发布审查确认：页面可以伪造 `postMessage` 状态并把任意字段带进后台诊断。
- 修复：bridge 只转发白名单字段，限制字符串长度、数组数量和整体 JSON 大小，降低诊断污染风险。

### 已应用：0.4.42

- 实时诊断确认：抖音刷下一条时会短暂出现多个非暂停 video，旧元素可能 `readyState=0` 但仍被旧逻辑算作有声。
- 修复：有声判断必须满足 `readyState >= 2`，降低过渡态误报。
- 增加 `MediaElementSource` 来源标记，后续可以区分占用来自本扩展还是页面/外部脚本。

### 已应用：0.4.43

- 实时诊断确认：失败元素 `sourceOwner=external`、`claimedByThisExtension=false`，说明页面脚本先于扩展创建了 `MediaElementSourceNode`。
- 根因：`play()` 钩子里视频还没 ready 时，扩展因 `readyState < 2` 跳过，随后页面脚本抢先占用同一个 video。
- 修复：`play()` 入口允许在有 src 且可见时预先创建 source，抢在页面脚本前建立 WebAudio 链路。

### 已应用：0.4.44

- 进一步确认：抖音仍可能先创建 external `MediaElementSourceNode`。Chrome 不允许扩展再创建第二个 source。
- 修复：`createMediaElementSource()` patch 保存 external source 节点；扩展遇到 external owner 时收编现有节点，断开原连接后接入平衡链路。
- 风险：如果页面原本在 external source 后面接了自己的复杂音频图，收编会绕过页面原图。但这是当前避免“当前元素受限”的必要路径。

### 已应用：0.4.45

- 实时诊断确认：`0.4.44` 已接管且无受限错误，但 `averageLiftDb=0`，说明提小声没有实际触发。
- 修复：提高提升目标、最大提升和峰值余量，降低真实小声信号的触发门槛；同时把 `currentLiftDb`、`momentaryDb` 写进媒体诊断，后续能直接看提升是否生效。

### 已应用：0.4.46

- 实时诊断确认：当前抖音有声 video `audible=true`、`readyState=4`，但 `src` 为空，旧逻辑按 `empty-src` 跳过，导致 `activeProcessorCount=0`。
- 修复：新增 `hasAttachableSource()` 和 `sourceKind` 诊断。没有 URL 但已经有可播放数据或 `srcObject` 的媒体允许接管；真正没有播放数据的空源仍然跳过。

### 已应用：0.4.47

- 诊断确认：磁盘版本已更新时，当前页面可能仍运行旧 engine；旧后台逻辑遇到 `staleEngine` 只返回刷新提示。
- 修复：后台在 stale 路径先停止页面旧 engine，再注入新 engine/bridge，减少抖音信息流因为刷新页面丢失当前视频的情况。

### 已应用：0.4.48

- 修复：扩展重载后主动补接当前活跃或正在发声的普通网页，减少“磁盘已更新但当前页仍跑旧内核”的窗口期。

### 已应用：0.4.49

- 实时诊断确认：直播页 `activeProcessorCount=1`、`connected=true`、`sourceKind=srcObject`、`engineVersion=0.4.48`，说明已经接管；但 `currentGainDb=0`、`averageReductionDb=0`、`averageLiftDb=0`，所以当时没有实际压低或提升。
- 修复：增加 analyser 输入诊断，记录输入响度、峰值、tick 数和 signal/silent 计数；桥接层不再把 nullable loudness 误转成 0。popup 将“保持”拆成“未调整”和“无波形”两种状态。

### 已应用：0.4.50

- 修复：popup 中 `audible > 0 && activeProcessorCount === 0` 的状态文案从“有声未处理”改为“当前声音未接入”，避免误以为插件已经在处理当前声音。

### 已应用：0.4.51

- 实时诊断确认：抖音直播页当前可听源为 `sourceKind=srcObject`，`audible=true` 且 `connected=true`，但 analyser 输入长期为 `lastInputDb=-90.691`、`lastPeak=0`、`signalTickCount=0`。这表示插件接到了 video 元素外壳，但 `MediaElementSourceNode` 路径没有拿到真实 PCM 波形。
- 修复：对带有 live audio track 的 `srcObject` 启用 `MediaStreamAudioSourceNode` fallback，不再强行走 `createMediaElementSource()`。fallback 会临时静音网页原始输出以避免双声，再用插件输出链路按播放器音量镜像处理；销毁处理器时恢复原始 muted 状态。
- 验收：新增 `tools/assert_stream_fallback.js`，检查 srcObject fallback、原声静音保护、播放器音量镜像、销毁恢复和状态统计。

### 已应用：0.4.52

- 实时问题确认：`0.4.51` 的直接 MediaStream 输出会绕过播放器静音语义。用户把播放器音量拉到 0 后，插件链路仍可能从 `srcObject` 输出声音。
- 修复：禁用 `srcObject` direct fallback。播放器静音、播放器音量 0、浏览器/系统音量上限优先级高于“尽量接管直播源”。当前拿不到波形时宁可显示无波形，也不能私自绕过用户静音。
- 后续要求：任何直播 fallback 必须先有可验证的静音/音量镜像方案，证明用户调到 0 时插件输出也为 0，再进入默认路径。

### 已应用：0.4.54

- 根因修复方向：直播 `srcObject` 的真实波形可能无法通过 `MediaElementSourceNode` 读取，但直接输出 `MediaStream` 会绕过播放器静音。安全方案是把 MediaStream 只作为分析输入，不连接到 `AudioContext.destination`。
- 修复：新增 volume fallback。对带 live audio track 的 `srcObject`，用 `createMediaStreamSource()` 接 analyser；根据响度只把原 `HTMLMediaElement.volume` 临时向下乘以 `0..1` 的系数。这样可以压大声，但不会把声音放到超过用户播放器音量，也不会在用户静音后继续发声。
- 限制：该路径不做真正的小声正增益。原因是任何超过原播放器音量的输出都可能违背“播放器/浏览器音量是上限”的约束。

### 已应用：0.4.56

- 实时问题确认：volume fallback 会拉动抖音直播自己的音量条。虽然它不超过播放器音量上限，但它把“音频处理”变成了“操控网站播放器 UI”，不符合插件定位。
- 修复：禁用并移除 volume fallback 状态，不再写 `HTMLMediaElement.volume`。插件只在能建立 WebAudio 输出链路时处理声音；不能安全接入时显示受限/无波形。
- 后续方向：直播 `srcObject` 的正确路线应是 `tabCapture + offscreen document` 或等价的浏览器级音频捕获处理，前提是验证不会绕过用户静音和系统/浏览器音量上限。

### 已应用：0.4.57

- 用户反馈：压大声和提小声拉到 100 时体感仍不明显，说明满档背后的实际 dB 范围偏保守。
- 修复：把最大压低从 34 dB 提到 48 dB，压低目标从 -39 dB 调到 -44 dB，瞬时过响阈值从 -34 dB 调到 -39 dB，峰值护栏从 0.42 收紧到 0.32，原生 leveler 比例从 12 提到 18。
- 修复：把提小声目标从 -32 dB 调到 -28 dB，最大提升从 26 dB 提到 34 dB，峰值余量从 0.7 放宽到 0.82，同时保留 limiter 和 headroom margin，避免把已接近削波的素材继续硬推。
- 边界：该增强只作用于已 WebAudio 接管且 analyser 能读到真实波形的音源。`srcObject` 直播如果只能显示“无波形/未处理”，不会通过修改网站音量条来伪造效果。

### 实验 A：响度窗口重构

目的：减少“忽大忽小”和“提小声不明显”的冲突。

- 保留 8 ms tick，但只用于采样。
- 主增益计算改用 400 ms 左右窗口。
- 压大声 attack 仍保持毫秒级。
- 提小声 attack 改为几十毫秒到百毫秒级，避免把每个字尾、噪声尾巴都拉起来。

验收：

- 人声视频里，句子开头不突然冲出来。
- 句中小声字能更清楚，但背景噪声不明显抬升。
- 音乐里鼓点不被削成一片，主旋律层次还在。

### 实验 B：动态目标而不是固定 dB

目的：不同视频不要都套同一个目标。

- 最近 3-10 秒估计素材自己的 loudness floor / median / high percentile。
- 大声目标跟随 high percentile 附近，避免把正常响亮段压得太死。
- 小声目标跟随 median 附近，不强行追到大声目标。

验收：

- 低音量视频会被托起。
- 已经很响的视频不会越开越大。
- 抖音连续刷视频时，下一条不会突然爆。

### 实验 C：正增益保护

目的：提升小声时不破音。

- 计算 peak headroom。
- 增加近似 true peak guard：用当前 sample peak 加安全余量，不把输出推到 0 dBFS 附近。
- 正增益触发 limiter 时，下一轮降低提升量，而不是继续硬推。

验收：

- popup 显示“提升中”时，声音更清楚但不毛刺。
- 如果素材本身已经破，插件不能让破音更明显。
- `提小声=0` 时绝对不出现正增益。

## 不做的方向

- 不做单纯 volume booster。
- 不用 `DynamicsCompressorNode` 作为唯一核心算法。
- 不把所有声音强行拉到同一个 sample peak。
- 不为了更明显牺牲播放器音量上限和防爆保护。
- 不在普通 popup 暴露专业参数，复杂诊断放后台页面。

## 调参原则

- 先压大声，再考虑提小声。
- 任何提升都要看峰值余量。
- release 不能太快，否则会听到忽大忽小。
- attack 不能太慢，否则会漏出未处理的大声。
- 历史原则是默认目标宁可偏低；现行实现已改为用开关前后中性校准选择节目中心，避免开启后平均基线系统性下降。
